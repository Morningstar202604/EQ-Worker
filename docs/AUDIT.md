### 已知限制：多进程并发写会丢记录（未修复）

**现象**：8 个 CLI 进程同时对同一数据文件执行 `add-person`，最终只保留 6–8 个，其余静默丢失；文件本身不损坏。

**原因**：写命令是「openStore（读快照）→ 改内存 → save（写回）」的复合操作。多个进程各自基于同一份旧快照，后写的覆盖先写的。这是纯文件后端的固有限制。

**为什么本轮不修**：尝试过两版方案（文件锁、锁内合并重读），都因为跨 adapter 缓存与锁嵌套问题未能稳定收敛，反而短暂引入了死锁（所有写入失败）。已回退到基线。

**实际影响面**：个人桌面/网页场景是单进程，无影响；CLI 与 MCP 若被同时调度（如同一台机器上跑脚本 + AI 客户端）才可能触发。

**下次的可行方向**（供决策，不是本轮承诺）：
- 简单方案：写前比对 mtime，变了就重读重放（乐观锁），冲突时让用户重试——实现简单，语义清晰
- 彻底方案：数据文件改为 SQLite（`node:sqlite` 已内置），用事务替代文件重写
- 规避方案：CLI/MCP 写入前 `flock` 整个命令生命周期，而不只是 save 段

### 本轮结论

**本地规则引擎的所有闭环均已验证通过**：录入→记账→参谋→结清→备份→恢复→跨端迁移→离线可用。

唯一未达标项仍是 AI 未进主应用（已按你的指示暂缓），以及上述多进程并发写限制（影响面明确、已记录）。
